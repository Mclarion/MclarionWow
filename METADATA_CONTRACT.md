## Storage and semantics

`{schema=1, spellCaptureEnabled=false, records={...}}`. Reputation/currency keys are `<entityType>:<decimalID>:<decimalBuild>:<locale>`; **spell keys append `:<observedBy GUID>`**. Keys are bounded to 128 bytes and checked against their records. `entityType` is exactly `reputation`, `currency`, or `spell`; positive integer ID/build ≤2,147,483,647; locale is 1–8 ASCII letters from `GetLocale()`. Each record has `entityType`, `id`, `build` (second `GetBuildInfo()` result from the already validated numeric capture), `locale`, `observedAt` (server seconds), `observedBy` (validated player GUID), `scope` (`character` or `account`), `name` (1–256 bytes); optional `description` (0–1,024 bytes), currency `iconFileID` (integer 0–2,147,483,647) and currency `quality` (integer 0–10). Empty API descriptions are treated as unavailable on refresh, preserving a known description for the same key; missing optional fields are **unknown**, not false/zero. Unknown fields, metatables, cycles/aliases, malformed keys/records and future schemas refuse metadata writes/readout without resetting old data. At most 400 variants and 524,288 conservative per-record charged bytes, plus the existing **combined six-root 3,000,000-byte structural projection**; this is not a game-serialized size or upload guarantee. Full metadata budget refuses new records without evicting existing variants. The callback sees a detached candidate and mutation is refused.

Metadata capture runs only for IDs from a successful opted-in/manual, two-pass visible-list numeric capture, including unchanged numeric observations. Missing optional API/locale/description or uncached ID leaves valid numeric capture intact, and does not delete known metadata. No guessed names or asynchronous lookup: a nil `GetCurrencyInfo`/`GetFactionDataByID` result stays unresolved until a later normal scan. The exact keyed variant replaces only with same/newer observation time. Metadata is descriptive; **quantity, standing, threshold, rank, active/collapsed state and other dynamic status stay in their existing owner/scope-specific histories**. Currency `scope` comes from guarded `isAccountWide`; reputation is character-only because its numeric writer refuses account-wide/unknown leaves. Account labels are shown only to the same current observing character; no cross-character authorization follows from the GUID. The read-only dashboard appends validated same-build/same-locale/current-observer names/descriptions beside IDs and escapes WoW control/pipe markup. Missing or invalid metadata leaves the numeric ID and value visible. The existing 32,768-byte details output cap still applies.

## Spell implementation (offline candidate)

The new owner retains `spellCaptureEnabled` (absent/false is off). `/vkmspells on` explicitly opts in out of combat; `/vkmspells off` opts out. Every successful opt-out through the public consent setter discards the private pending queue and invalidates scheduled wakeups, including callers outside the slash command. Only the pinned-client `UNIT_SPELLCAST_SUCCEEDED` event's validated `unitTarget == "player"` and numeric `spellID` feed a deduplicated 64-ID memory queue. Cast GUID and all other payloads are discarded. Enrichment is out of combat, at most four IDs per wakeup, with up to three attempts for missing text and a two-second timer when available; `PLAYER_REGEN_ENABLED`, `SPELL_TEXT_UPDATE` and `SPELL_DATA_LOAD_RESULT` also wake pending IDs. Missing text invokes `C_Spell.RequestLoadSpellData` only for an observed spell ID. No spellbook traversal, gameplay action, combat-log event storage, cast/damage observation or inferred learned state. Optional metadata refusal does not gate existing numeric histories. The slash command is a consent control, not an arbitrary ID lookup.

`spell` records use character scope, original icon if available (otherwise iconID), name and optional nonempty description with `descriptionProvenance="player-spellcast:C_Spell.GetSpellDescription"`; their key includes build/locale/**observer**, and record carries observer/time. Description is **contextual** to that player/client, not an immutable effect/damage fact. Nil/empty/invalid asynchronous results do not erase prior fields for that observer, and no contextual field is copied from another observer. Each observer's record has independent read-only lookup; there is no migration from a previously released metadata schema. No cooldown, cast time, cost, range or current damage is stored. Read-only `Spells` dashboard renders the validated same-observer/build/locale records, escapes markup and caps output; absent metadata remains absent, not a spellbook claim. Quests are excluded.

## Requested entity inventory and staged roadmap

- **Items:** existing schema-2 `MHWOWI1` already retains names, description, quality, icon, link and many attributes for cached observed bag/equipment/own-bank IDs. Reuse rather than duplicate; stage normalization into the separate metadata root only after matching each observed ID to actual source/page/build/locale and testing cache-unavailable behavior. Quantities remain in histories.
- **Factions:** implemented under `entityType=reputation`; name/description only, no global standing. Visible character-scoped IDs only.
- **Currencies:** implemented under `entityType=currency`; name/description/icon/quality plus provenance, no global balance. Visible ID list only.
- **Spells:** offline candidate implemented for consented successful player-spellcast IDs, localized name/icon and contextual description, not rank, spellbook or cast history. See source and limitations above.
- **Maps:** legacy character snapshots have an observed map ID. Stage localized map name and parent/area relation only if an exact-client lookup is documented and a bounded observed-ID path exists; no map traversal or inferred visits.
- **Titles:** `MHWOWT1` saves selected/known mask IDs. Stage only observed IDs against exact-client title APIs; distinguish mask IDs from other title identifiers and retain locale/grammatical form, never acquisition time.
- **Talents:** no validated numeric talent history; establish observed tree/node/rank identity, specialization/owner context and exact Forever APIs first. Do not flatten contextual rank into a universal title.
- **Professions:** no validated profession history; establish actual observed skill/recipe ID namespace and owner/skill context before names, no inferred completion or recipe enumeration.
- **Quests:** explicitly excluded from the new static metadata file; active quest IDs remain in `MHWOWQ1`, not completion history. Existing quest records are not enriched by this batch.

Every future entity needs an explicit typed ID namespace, build/locale, observed time and provenance, optional-field semantics, source-matched API evidence, strict size budget, read-only escaped display, synthetic Lua 5.1/5.4 and package regressions, and independent consumer compatibility before import/release.
